01结论摘要

在当前硬件上，应用可以稳定运行，但存在两个明确的性能悬崖： 一是本地资源列表非虚拟化渲染，内存随曲库线性增长约 57 MB/千首、切页卡顿约 2 s/万行； 二是 MV 播放走 ffmpeg 软件解码，1080p 需持续占用 4–5 个逻辑核。 前者决定了「大曲库会不会崩」，后者决定了「低端机会不会卡」。

使用档位硬件建议可用曲库规模视频结论
最低可运行 4 GB RAM · 双核 · 集显 · HDD · 1280×720 ≤ 2,000 首 720p 软解勉强 可用但会卡
推荐 8–16 GB RAM · 4–6 核 · 支持 OpenGL 3.3 · SSD ≤ 10,000 首 1080p 硬解流畅 流畅（切页仍有 ~2 s 停顿）
理想 16 GB+ · 8 核+ · 独显硬解 · NVMe ≤ 30,000 首 1080p/4K 硬解 流畅
高风险 ≤ 4 GB RAM，或曲库 > 5 万首 > 50,000 首 4K 软解 可能 OOM / 长时间无响应
最重要的一条：按实测 57 MB/千首线性外推，10 万首曲库将需要约 5.7 GB 额外内存。 在 8 GB 或 16 GB 机器上直接触发内存耗尽（Windows 会先疯狂换页 → 界面假死 → 进程被终止）。 这是当前版本唯一的「必崩」路径。

启动阶段不是瓶颈：本地计算只占约 0.5 s，其余都是「等网络 + 等动画」。 真正的感知延迟来自引导页固定时长——即使数据 1.3 s 就绪，用户仍要等到 3.8 s 才能看到主界面。

弱网影响：首屏并发 12 个 weapi 请求（catlist / album-new / djprogram / toplist / recommend / hot-search 等）。 在有代理或高延迟网络下，data-ready 会从 1.3 s 拉长到 2.4 s 以上； 若某请求超时，引导页可能长时间停留。这是「启动看起来卡住」的首要原因。

结论 1：GL 后端工作正常

空闲 CPU 仅 3–4%（单核口径），线程数在启动后 60 s 内收敛到 28–33， 说明没有明显的轮询泄漏或空转循环。首次启动 70 个线程属于网络/解码线程池预热。

结论 2：软件渲染并非「必然更差」

本次实测软件渲染的空闲 CPU（1–2%）与内存（447 MB）都优于 GL 后端。 但这是 900×560 级窗口的静态画面结果。窗口放大、4K / 高 DPI、滚动与动画场景下软件光栅化会急剧恶化， 且会与视频解码抢占 CPU 核心。不能据此推断「无 GPU 的机器体验更好」。

内存绝对值偏高：空库即 520–585 MB，对桌面音乐播放器属于偏高水位。 主要来自 Slint 组件树、图像解码缓存（dcache 预算 256 MB）、 ffmpeg 静态库以及 tokio 线程栈。低内存机器（4 GB）在此基线上再叠加大曲库会非常危险。

稳态 CPU 在 367%–507% 之间波动（换算为 3.7–5 个逻辑核）， 对一台 6 核 12 线程的机器意味着占用约 30–42% 的总算力。 内存稳定在 1.10 GB（其中包含上一节的 1 万首曲库列表），播放期间无明显增长，说明解码缓冲没有泄漏。

虽然标记为「硬解」，CPU 仍然很高

日志显示 dxva2 已启用，但 CPU 仍在 4–5 核。硬解只覆盖解码， 色彩空间转换（NV12→RGBA）、缩放、以及 Slint 的上屏合成仍走 CPU。 这部分开销与窗口尺寸正相关，窗口越大越明显。

对低端机的含义

4 核机器上播放 1080p 会直接占满全部核心，导致：音频缓冲抖动（爆音）、 界面拖动掉帧、其他应用无响应。双核机器基本不可用。 4K 片源在没有硬解时会彻底不可用。

测量限制：本轮 VIDEO_ROW_FOUND = False， 自动化脚本未能通过 UIA 名称匹配到视频行并完成「点击播放」的完整路径校验， 但日志与 CPU/内存曲线证明播放确实已发生，上述数据成立。视频行的可访问性名称匹配问题建议单独排查。

09优化建议

P0

把 SongList 改为虚拟化列表（ListView）

这是唯一能消除「必崩路径」的改动。用 ListView + 固定行高， 只实例化视口内约 15–20 行，行数据通过索引按需取。 同步改造本地页的视频列表（当前也是裸 for）。

涉及：ui/components/songlist.slint、ui/pages/local/local.slint

预期：内存 574 MB → < 40 MB；切页 2 s → < 50 ms
P0

扫描结果分批增量推送，而不是一次性替换模型

当前扫描完成后在 invoke_from_event_loop 里一次性替换整个 VecModel， 导致 UI 线程被占用约 2 s。改为每 500 条推送一次， 并让 UI 有机会在两个批次之间处理输入事件。

涉及：src/handlers/local.rs 的 start_scan 回写段

预期：扫描完成瞬间的 2 s 白屏 → 逐批出现，单批 < 60 ms
P1

为 walk_files 增加符号链接/junction 去重与深度上限

用 std::fs::canonicalize 或 metadata.file_type().is_symlink() 跳过链接， 并限制递归深度（如 32 层）。这是目前最容易被用户目录结构触发的崩溃点。

涉及：src/network/netease/local.rs

预期：消除无限递归风险
P1

搜索过滤加防抖 + 复用已有模型

输入停顿 200 ms 后再过滤，并用 set_row_data 原地更新， 避免每次按键都重建两个 VecModel。

涉及：src/handlers/local.rs 的 apply_filter

预期：万首量级输入顿挫消除
P2

封面缓存预算按物理内存自适应

当前 dcache 固定 256 MB（600 px RGBA ≈ 1.44 MB/张，约 177 张 FIFO）。 在 4–8 GB 机器上，这个固定值叠加曲库内存后很容易触顶。 建议改为 min(256 MB, 物理内存 / 16)。

涉及：src/load/home/covers.rs

预期：低内存机器节省 100–200 MB
P2

大曲库预警 + 扫描进度反馈

扫描超过 5,000 个文件时在页面顶部提示「大曲库可能影响流畅度」； 扫描过程中显示已处理数量（当前只显示「扫描中…」），避免用户误以为卡死而强杀进程。

涉及：ui/pages/local/local.slint、src/handlers/local.rs

P3

渲染后端回退时给出可见提示

require_opengl() 失败后静默走软件渲染，用户只会觉得「这软件卡」。 建议在设置页显示当前渲染后端，并在回退时记录一次性提示。

涉及：src/main.rs

P3

视频播放区分「解码」与「上屏」成本

DXVA2 已启用但 CPU 仍占 4–5 核，说明瓶颈在色彩空间转换与合成。 可尝试把视频帧直接交给 GPU 采样（避免 CPU RGBA 转换），或在窗口较大时降低合成分辨率。

涉及：src/handlers/mv/player.rs、src/handlers/mv/mv_decoder_hw.rs
